## 4. Knowledge-Driven Source Resolution

This program is knowledge-driven, not file-driven.

Phases do not depend on a fixed list of files. Phases declare the categories of knowledge they require, then resolve the best available source for each category through the official Source Resolution Contract.

Concrete files are current implementations of knowledge categories. If a better source appears later, the program may use it without changing the program architecture, provided the source resolves through the required owner, truth, freshness, confidence, and superseded-state checks.

Reports remain evidence. They do not become truth owners unless promoted through the existing canonical owner path.

### Situation-Aware Autonomous Behaviour Model

The primary analysis entity of this program is:

```text
Autonomous Behaviour
```

Autonomous Behaviour has two official analytical levels:

```text
Behaviour Definition
  -> Behaviour Instance
```

`Behaviour Definition` is the canonical type of behaviour. It describes what kind of behaviour exists in V7.

`Behaviour Instance` is a concrete occurrence or execution of a Behaviour Definition in a specific current reality.

All program phases analyze Autonomous Behaviour through this split. They do not analyze files, documents, functions, components, or the system as primary entities. Those surfaces are evidence, discovery indexes, owners, or implementation representations of Behaviour Definitions and Behaviour Instances.

### Behaviour Definition

Behaviour Definition is a canonical Behaviour type.

It is not execution, not Runtime, not an event, and not an instance.

Examples:

- Channel Recovery;
- Channel Promotion;
- Routing Selection;
- Incident Escalation;
- Rollback;
- Verification;
- Learning;
- Engineering Report Generation;
- Canonical Synchronization;
- OMP Mission Routing;
- Authority Approval;
- Runtime Apply;
- Production Certification;
- Knowledge Evolution.

Behaviour Definition is used by:

- Behaviour Catalogue;
- Behaviour Coverage;
- Behaviour Graph;
- Behaviour Classification;
- Behaviour Maturity.

Behaviour Definition creates no owner, no Runtime, no Planner, no Authority, no roadmap, and no truth source.

### Behaviour Instance

Behaviour Instance is a concrete occurrence of a Behaviour Definition in a specific situation and reality.

A Behaviour Definition may have many Behaviour Instances.

Example:

```text
Behaviour Definition: Channel Recovery
Behaviour Instances: every concrete Channel Recovery occurrence in a specific situation.
```

Only Behaviour Instance passes through the full operational chain. Behaviour Definition does not execute.

Official chain:

```text
Behaviour Definition
  -> Behaviour Instance
  -> Situation
  -> Context
  -> Interpretation
  -> Applicable Knowledge
  -> Applicable Laws
  -> Possible Decisions
  -> Decision Selection
  -> Execution
  -> Verification
  -> Learning
  -> Improvement
  -> Canonical Sync
  -> OMP
  -> Updated Behaviour Definition if required
  -> Next Behaviour Instance
```

Behaviour Instance internal chain:

```text
Situation
  -> Context
  -> Interpretation
  -> Applicable Knowledge
  -> Applicable Laws
  -> Possible Decisions
  -> Decision Selection
  -> Execution
  -> Verification
  -> Learning
  -> Improvement
  -> Canonical Sync
  -> OMP Continuation
  -> Next Situation
```

`Context` is not a new owner. `Possible Decisions` are not a Planner. `Decision Selection` is not Runtime. They are analytical stages inside Autonomous Behaviour.

Reasoning remains required as the evidence and explanation layer inside `Decision Selection`; it is not removed and does not create a new Planner.

Law Execution is only one segment of Autonomous Behaviour. A law cannot be executed autonomously until the system has interpreted the situation, resolved context, selected applicable knowledge and laws, identified possible decisions, reasoned about constraints, and selected a legal decision or no-action.

This model creates no owner, no Runtime, no Planner, no Authority, no roadmap, and no truth source. It is an analytical schema for this program.

### Behaviour Discovery Rule

Behaviour Discovery first searches for a Behaviour Definition.

If an existing Behaviour Definition is found, Phase 2 may create or record Behaviour Instances under that Definition.

If no Behaviour Definition exists, the program may create a new Behaviour Definition only through the mandatory order:


```text
Discover
  -> Reuse
  -> Extend
  -> Create only if necessary
```

A Behaviour Definition may be created only when no existing Behaviour Definition, owner, source, evidence path, Function Graph relationship, Knowledge Graph relationship, OMP mission pattern, Runtime rule, Decision Model rule, or canonical knowledge entry already covers it.

If an equivalent Behaviour Definition exists, the program must reuse it. If an existing Behaviour Definition is partial, the program must extend its record through the existing owner path. Duplicate Behaviour Definition records are forbidden.

Behaviour Instances do not create new Behaviour Definitions by default. They provide evidence for existing definitions unless the Behaviour Discovery Rule proves that no existing definition covers the instance.

### Source Resolution Model

Each Knowledge Category resolves sources by rule, not by hard-coded file name.

For every required category, the phase must find the best available source related to that category and evaluate:

- Canonical Owner;
- Truth Level;
- Freshness;
- Owner Authority;
- Current Status;
- Confidence;
- Staleness;
- Superseded state.

The selected source must be the highest-authority available source for that category at the time of execution. A lower-priority source may be used only as evidence, discovery, historical context, or manual-review input when the higher-priority source is absent, stale, superseded, or not applicable.

### Source Resolution Contract

Before Foundation Consumption and before any phase operation, the phase execution record must:

1. determine the required Knowledge Categories for the phase;
2. discover candidate sources for each required category;
3. check Truth Level, Freshness, Owner, Confidence, Staleness, and Superseded state;
4. select the best available source for each category;
5. record the resolution decision;
6. only then perform Foundation Consumption and phase execution.

If any required category cannot be resolved to a source, terminal alternative, or deterministic not-applicable decision, the phase must return `AUTONOMOUS_EVOLUTION_PROGRAM_HOLD`.

### Knowledge Source Contract

Every resolved source must record:

| Field | Meaning |
|---|---|
| Knowledge Category | Category being satisfied. |
| Source | Concrete current source, source family, owner endpoint, report, code surface, evidence surface, or terminal not-applicable decision. |
| Owner | Existing owner responsible for the source or category. |

| Decision Weight | Whether the source may affect decisions or only inform discovery/evidence. |
| Required | Whether the source is mandatory for the phase. |

### Knowledge Resolution Priority

When multiple sources satisfy one Knowledge Category, the official priority is:

```text
Canonical Owner
  -> Locked Knowledge
  -> Locked Architecture
  -> Canonical Reference
  -> Supporting Canonical Sources
  -> Current Reality
  -> Implementation Reality
  -> Evidence
  -> Historical Context
```

The source with the maximum valid priority must be selected. Evidence and historical context may not override locked or canonical truth, but they may prove staleness, trigger owner review, or route Knowledge Evolution.

### Law / Rule Source Resolution Rules

Law and rule discovery reuses the Knowledge Category model. It does not replace it.

When a phase needs to understand a law, rule, policy, decision logic, runtime rule, routing rule, channel rule, verification rule, rollback rule, learning rule, or synchronization rule, it must resolve the law through the same Source Resolution Contract:

1. identify the situation or behaviour where the law may apply;
2. resolve the highest-authority source for the law through the relevant Knowledge Category;
3. identify the existing law owner;
4. determine whether the law is current, stale, superseded, historical, or not applicable;
5. determine whether the law can affect decisions;
6. determine the current execution, verification, learning, and sync path if any;
7. record the law in an Autonomous Behaviour Unit or Law Execution Unit.

Discovery indexes may help find laws, but they do not create laws.

Reports may prove law execution or non-execution, but they do not become law owners unless promoted through an existing canonical owner path.

### Chain Closure Law

Every program element is complete only when its end state becomes the input of the next element or when it is recorded as a proven terminal state.

Assigning a consumer is not sufficient. The consumer must confirm consumption before the result can close its lifecycle.

Official result lifecycle:

```text
Producer
  -> Result Produced
  -> Consumer Assigned
  -> Consumer Consumed
  -> Consumption Confirmed
  -> Next Action
  -> Chain Closed
```

This law applies to:

- phases;
- actions;
- artifacts;
- Autonomous Behaviour Gaps;
- missions;
- implementation outputs;
- verification results;
- evidence;
- learning;
- canonical sync;
- reports;
- program state.

Forbidden orphan outcomes:

- action without next consumer;
- artifact without consumer;
- report without consumption path;
- evidence without verification, maturity, or learning consumer;
- Autonomous Behaviour Gap without mission or terminal rejection;
- mission without implementation, hold, or impossibility state;
- implementation without verification, evidence, learning, and canonical sync;
- verification without closure;
- closure without report or state update;
- report without owner consumption;
- current state update without next action;
- Foundation update without Foundation Verification;
- program state without unlock rule or terminal hold.

If an element has no next consumer, it may close only when an existing owner records a terminal alternative.

Allowed closure statuses:

- `NOT_PRODUCED`;
- `PRODUCED`;
- `ASSIGNED`;
- `CONSUMED`;
- `CONFIRMED`;
- `CHAIN_CLOSED`;
- `CHAIN_HOLD`;
- `CHAIN_CONTINUES`;
- `TERMINAL_ACCEPTED`;
- `TERMINAL_REJECTED`;
- `TERMINAL_HOLD`;
- `TERMINAL_IMPOSSIBLE`;
- `STOP_SAFE`.

Every closable element must record:

|---|---|
| Element | Phase, action, artifact, Autonomous Behaviour Gap, mission, implementation output, verification, evidence, learning, canonical sync, report, or program state. |

| Terminal Alternative | Terminal accepted/rejected/hold/impossible/STOP_SAFE path when no next consumer exists. |
| Closure Status | One of the allowed closure statuses. |

If `Consumer` is absent, `Terminal Alternative`, `Owner`, `Evidence`, and `Closure Status` are mandatory. Otherwise the element is not closed.

If `Consumer` is present but `Consumption Evidence` is absent, the element is not closed.

## 12. Autonomous Behaviour Gap Certification Rules

An Autonomous Behaviour Gap is not a mission until it is certified.

An Autonomous Behaviour Gap belongs to a Behaviour Instance.

It does not belong directly to a Behaviour Definition, but its result must be aggregated back to the Behaviour Definition through the Behaviour Aggregation Model.

Before an Autonomous Behaviour Gap can be certified as real, Phase 3 must perform the Behaviour Definition, Behaviour Instance, situation, context, applicable-knowledge/law, possible-decision, decision-selection, reasoning-evidence, existing-knowledge, and existing-implementation check:

- verify whether the Behaviour Instance is real, current, stale, historical, or not applicable;
- verify whether the Behaviour Definition exists in the Behaviour Catalogue or must be created under the Behaviour Discovery Rule;
- verify Behaviour Coverage, Behaviour Classification, and Behaviour Maturity for the Behaviour Definition;
- verify whether the Behaviour Instance is correctly aggregated to its Behaviour Definition;
- verify whether the situation is real, current, stale, historical, or not applicable;
- verify whether context is known, stale, missing, ambiguous, or not applicable;
- verify whether the situation interpretation already exists and resolves to an official owner;
- verify whether applicable knowledge and applicable laws have been selected through Source Resolution;
- verify whether possible decisions are known and bounded;
- verify whether decision selection and reasoning evidence already exist;
- verify whether the required knowledge already exists in resolved Knowledge Maps and resolves to an official owner;
- verify whether the required implementation already exists in resolved Implementation Maps or current implementation evidence;
- verify whether an existing owner already owns the responsibility;
- verify whether an existing consumer already consumes the capability or knowledge;
- verify whether automation state and manual dependency classification are known;
- verify whether verification, rollback/no-rollback, learning, and canonical sync paths exist;
- verify whether a ready integration path already exists.

### Gap Priority Model

Certified Autonomous Behaviour Gaps must be prioritized before they are offered to OMP as mission candidates.

Priority is determined by the following ordered criteria:

| Criterion | Meaning |
|---|---|
| Situation criticality | Severity and urgency of the real situation the system cannot yet understand or handle autonomously. |
| Law criticality | Importance of the existing law/rule/policy that is not yet applied or executed autonomously. |
| Human-dependency reduction | Degree to which closure removes routine human or Codex interpretation, decision, execution, verification, learning, or sync work. |
| Production impact | User/service/reliability impact if the gap remains open. |
| Decision safety | Degree to which closure improves safe no-action/action selection without expanding authority unsafely. |
| Learning impact | Degree to which closure improves feedback quality and future autonomous reasoning. |
| Autonomy impact | Degree to which the gap blocks movement toward governed autonomous operation. |
| Prerequisite status | Whether the Autonomous Behaviour Gap unlocks other certified Autonomous Behaviour Gaps or phases. |
| Dependency weight | Number and criticality of downstream owners, functions, or missions depending on the gap. |
| Engineering debt reduction | Degree to which resolving the gap removes repeated manual work or architectural drag. |
| Automation gain | Degree to which resolving the gap advances certified automation without expanding authority unsafely. |
| Blast radius | Risk surface of implementing or leaving the gap unresolved. Lower safe blast radius may raise execution readiness; high blast radius may require certification first. |
| Capability unlock | Whether the gap unlocks a named capability, action class, production certification step, or maturity category. |
| Evidence availability | Whether sufficient real evidence exists to execute or certify safely. |
| Implementation complexity | Effort and uncertainty required to resolve through existing owners. |

Every certified Autonomous Behaviour Gap must receive one priority class:

- `P0_PRODUCTION_BLOCKER`;
- `P1_AUTONOMY_BLOCKER`;
- `P2_CAPABILITY_UNLOCK`;
- `P3_ENGINEERING_DEBT`;
- `P4_OPTIONAL_OPTIMIZATION`;
- `HOLD_INSUFFICIENT_EVIDENCE`;
- `HOLD_AUTHORITY_OR_BLAST_RADIUS`;
- `REJECTED_DUPLICATE_OR_NOT_REAL_GAP`.

OMP must receive a prioritized stream of certified mission candidates, not an unordered Autonomous Behaviour Gap list.

Priority does not grant authority, bypass certification, change OMP ownership, or permit implementation outside existing owners.
