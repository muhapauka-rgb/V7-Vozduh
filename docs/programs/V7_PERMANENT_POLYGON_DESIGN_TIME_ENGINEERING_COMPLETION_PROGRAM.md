# V7 Permanent Polygon Design-Time Engineering Completion Program

Status: APPROVED_EXECUTION_PLAN

Activation state owner: CPS

This file must not be used to determine whether the Master Program is active, paused, terminal or waiting.

Program ID: `V7_PERMANENT_POLYGON_DESIGN_TIME_ENGINEERING_COMPLETION_PROGRAM_V1`

Target terminal: `PERMANENT_POLYGON_DESIGN_TIME_SEMANTIC_DIFFERENTIAL_REPAIR_CALIBRATION_LOOP_CERTIFIED`

## Objective

Turn the existing Permanent Polygon into a design-time engineering system which continuously converts an owner-backed product intent or change into an exact, risk-driven validation campaign; compares baseline and proposed behaviour semantically; minimizes and classifies counterexamples; routes real V7 defects through the existing BDP/OMP owners; verifies the repair; and hands the consumed result to the next product-development frontier.

The required closed chain is:

`PRODUCT INTENT OR CHANGE -> DESIGN CHANGE CONTRACT -> AFFECTED OBLIGATIONS -> BASELINE/PROPOSED EXECUTION -> SEMANTIC DIFFERENTIAL -> COUNTEREXAMPLE -> CLASSIFICATION -> BDP/OMP REPAIR -> REAL SOURCE CHANGE -> TEST/COMMIT/SAFE DEPLOY/PRODUCTION CALLER -> TRUTH/CONVERGENCE -> CALIBRATION -> NEXT RISK OR NEXT PRODUCT FRONTIER`

No stage may terminate with an unconsumed report. Every terminal must identify its real consumer and either materialize a successor obligation or prove that no owner-backed work remains.

## Permanent laws

### Discover, reuse, extend, implement

Before adding any function, adapter, schema, owner or state:

1. search the repository by name, contract, producer, consumer and behaviour;
2. reuse an existing implementation when its semantics satisfy the criterion;
3. extend the last responsible existing owner when semantics are partial;
4. implement a new component only when the capability is proven absent;
5. record the semantic duplication decision in the Mission report.

### Owner and truth law

- OMP remains the engineering-program and Mission owner.
- BDP remains the development-impulse and candidate-admission owner.
- CPS remains the only live program-state owner.
- Existing V7 Planner, Decision, Runtime, execution, feedback and Learning owners remain authoritative for their behaviours.
- The Polygon may model, execute in isolation, compare, recommend and certify engineering evidence. It may not create a second Planner, Runtime, scheduler, queue, truth source, production authority or Production Maturity owner.

### Evidence and defect-separation law

Every mismatch must be classified before repair as one of:

- invalid fixture or input;
- Polygon model defect;
- harness defect;
- oracle defect;
- generator defect;
- unsupported substrate;
- resource-bound violation;
- non-determinism;
- reproducible V7 real-source defect;
- bounded automation-path certification evidence.

Only a reproducible V7 real-source defect may become a product repair candidate. Harness, model, oracle and generator defects stay in the engineering plane. Synthetic evidence never receives controlled or natural production credit.

### Bounded repair and production law

A real V7 repair must preserve the exact failing identity and use the existing engineering workflow:

`MINIMIZED COUNTEREXAMPLE -> BDP -> OMP MISSION -> LAST RESPONSIBLE SOURCE OWNER -> TESTS -> COMMIT -> tools/v7-safe-deploy -> PRODUCTION NON-TEST CALLER -> TRUTH -> CONVERGENCE -> SAME COUNTEREXAMPLE REPLAY -> AFFECTED REPLAY -> INTENT CLOSURE`

The Polygon must never arbitrarily self-patch production. Production deployment is permitted only through `tools/v7-safe-deploy` with a reviewed manifest and unchanged authority boundaries.

### Dynamic Mission compression

The Missions below define required capability stages, not mandatory empty execution containers.

After every Mission, OMP must recalculate remaining criteria. If a later Mission is already fully closed by valid consumed evidence, record `MISSION_NOT_REQUIRED_ALREADY_CONSUMED` and continue. If partially closed, reduce it to the exact remaining criteria. Missions may be merged only when owner, completion contract, isolation, verification and terminal semantics remain explicit.

### Substrate degradation

Absence of one fidelity substrate must not stop independent lower-fidelity or logically equivalent work. Prove the exact missing substrate, continue every independent criterion at the highest honest available fidelity, persist the higher-fidelity residual, and stop the program only when no independent criterion can continue. Missing L3/L4 substrate is not a global `REAL_WORLD_LIMIT`.

## Missions

### Mission 0 — Residual truth and semantic reuse baseline

Reconcile CPS, corpus, source owners, existing Polygon functions, reports, tests and production snapshot. Produce a semantic reuse/gap map and prove which capabilities already exist. Completion requires an exact remaining frontier, not a name-based inventory.

### Mission 1 — Design Intent and Change Compiler

Extend the existing Permanent Polygon source adapter so an owner-backed product objective, source/policy/topology change or commit range compiles into:

- a validated design-change contract;
- affected dependencies, invariants, owners, capabilities and scenarios;
- baseline and proposed snapshot identities;
- exact validation obligations and fidelity requirements;
- an OMP-consumed successor frontier.

Documentation-only or non-semantic changes must yield an explicit no-execution decision with reason.

### Mission 2 — Baseline/proposed semantic differential

Run identical obligations against baseline and proposed source snapshots through the existing V7 owners. Compare stable behaviour rather than text or timing: decisions, selected moves, terminals, invariant verdicts, safety effects and declared collateral changes. Fail closed on undeclared semantic deltas.

### Mission 3 — Counterexample minimization and classification

For a reproducible mismatch, deterministically reduce scale, topology, events, faults, recoveries and service dimensions while preserving the same failed invariant and terminal. Classify the minimized result using the evidence/defect-separation law and route only eligible V7 defects into BDP/OMP.

### Mission 4 — Protocol, tunnel and datapath fidelity

Reuse the existing L2 and Docker/Linux L3/L4 lanes, then extend them with criterion-scoped V7 WireGuard/AmneziaWG, OpenVPN and VLESS/Xray configuration and lifecycle contracts. Execute real protocol/data-plane fidelity only when the isolated substrate exists. Persist exact unsupported higher-fidelity criteria without blocking independent work.

### Mission 5 — Bounded real-source repair and return

Prove the full repair path using a disposable source snapshot/worktree and the same counterexample. A certification drill may prove automation mechanics but must not be labelled a natural product defect. The Mission remains partially open until an actual Polygon-found V7 source defect is repaired, committed, safely deployed, consumed and replayed.

### Mission 6 — Historical replay and calibration

Reuse existing outcome, trust, feedback, shadow Learning and calibration owners. Compare predicted engineering outcome with owner-backed actual outcomes; emit accuracy, error and drift metrics; invalidate dependent criteria when thresholds fail; never promote synthetic evidence to production confidence.

### Mission 7 — Risk coverage and feedback generation

Replace count-oriented sufficiency with a risk model spanning owners, invariants, protocols, failure/recovery sequences, legal negative terminals, scale boundaries, semantic change surface, mutation strength and calibration error. Coverage gaps must generate exact next obligations; closed risk criteria must be consumed and retired.

### Mission 8 — CI, PR, deploy and final end-to-end certification

Integrate selective low-fidelity validation into repository CI and expose bounded high-fidelity/manual lanes without production credentials. Certify one complete non-test chain from design objective to code effect, commit, safe deployment, production caller, truth/convergence, calibrated replay and exact next frontier. Update CPS atomically and emit the target terminal only when every required criterion is consumed.

## Completion contract

The program is complete only when all of the following are true:

- a product-development objective or source change is a real Polygon input;
- semantic discovery produces the exact affected obligation set without duplication;
- baseline/proposed executions reach existing V7 owners;
- semantic differential and counterexample minimization are deterministic;
- mismatch classification prevents Polygon defects from becoming product fixes;
- at least one eligible real-source repair follows the bounded commit/deploy/production-consumer path, or the absence of a natural defect is preserved as an explicit non-terminal residual;
- historical calibration changes future risk/obligation selection;
- risk insufficiency creates a successor scenario and closure retires it;
- CI validates the appropriate lane;
- every output has a real consumer and every Mission terminal creates or selects the next frontier;
- local, GitHub and production commit/runtime snapshot agree after deploy;
- Runtime apply, routing mutation, user movement, packet execution, restore-barrier write, rollback apply, daemon/timer enablement, Authority expansion and Production Maturity promotion remain absent unless separately authorized by their existing owners.
