# Engineering Report — создание профиля Лизы и проверка видимости в админке

Дата: 2026-08-27 (MSK)
Контур: текущий V7 Runtime; после диагностики выполнено минимальное исправление
Admin API и штатный safe deploy.

## Запрос

Создать человека `Лиза`, телефон (последние 4 цифры: `4399`), выдать первый профиль на
канале `vless` и проверить, что запись видна через административный контур.

## Причина отказа в админке

До операции глобальный Safe Mode был включён:

- `enabled=true`, `state=OPEN`;
- причина: `selected_moves_applied`;
- все изменяющие действия админки, включая создание пользователя, штатно
  возвращали `safe_mode_enabled` (HTTP 423).

Это объясняет, почему ручное создание клиента не проходило. Защита не была
сломана и не обходилась.

## Выполненное действие

Использован существующий admin identity owner и короткое operation-scoped окно:

1. выполнен dry-run штатного identity-потока для телефона и `vless`;
2. preflight подтвердил свободный IP `10.7.0.125` и таблицу `1123`;
3. через тот же owner выполнено создание identity, IPAM lease, WireGuard-
   совместимого устройства и Karing-профиля;
4. Safe Mode немедленно возвращён в `enabled=true`, `state=OPEN` в `finally`.

Никакие registry/state-файлы вручную не редактировались, новый owner или
route writer не создавались.

## Видимость в административном контуре

Свежий `identity_state()` (тот же read-model, который использует Admin API)
вернул Лизу и её устройство. Сводка после операции: 16 identity users, 15
active devices, 11 active allowed users. Следовательно, после входа в Admin UI
запись должна отображаться в разделе пользователей/идентичностей.

## Почему экран мог не показывать Лизу

Свежие журналы Admin API показали: медленный read-only запрос обновления снимка
состояния завершался тайм-аутом, а обработчик затем падал на сложении
бинарного вывода с текстом (`TypeError`). Поэтому браузер не получал новый
`overview`, хотя запись уже была в канонической базе.

Исправлено только преобразование `bytes` в UTF-8 текст в обработчике тайм-аута
`run_json_command`; добавлен регрессионный тест для Python 3.14.

- production hash Admin API совпадает с опубликованным;

- прежний read-only autoswitch запрос после deploy завершился штатным JSON

## Проверки безопасности и эффекта

- `v7-user-route-check`: `V7_USER_ROUTE_CHECK=OK`;
- для `10.7.0.125`: registry и assignment = `vless`, покрытие проверенным
  Core-primary routing подтверждено;
- ordinary users не перемещались и не изменялись;
- Safe Mode после операции снова глобально открыт для чтения и блокирует
  дальнейшие изменения;
- изменён только Admin API и его регрессионный тест; маршруты, клиенты,
  cadence, Matrix и Runtime semantics не менялись;
- safe deploy перезапустил только `v7-admin-api.service`.

## Ограничение

В момент создания VLESS имел частичную деградацию по полной матрице, хотя
Telegram-only проверка проходила. Поэтому профиль создан на запрошенном канале,
но стабильность VLESS нужно наблюдать отдельно; автоматическое переключение
для него по-прежнему запрещено его текущей политикой.

## Следующий шаг

Открыть Admin UI заново (полная перезагрузка страницы после входа) и найти
`Лиза` по имени или IP `10.7.0.125`. Если экран всё ещё показывает старый
список, выйти и войти снова: серверный read-model и API уже подтверждают
запись. После визуальной проверки — отдельно подтвердить фактическую
доступность VLESS для нового IP и, если канал остаётся нестабильным, через
существующий owner перевести Лизу на здоровый канал.
