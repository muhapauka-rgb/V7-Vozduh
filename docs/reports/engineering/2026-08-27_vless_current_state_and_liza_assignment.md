# Engineering Report — текущее состояние VLESS и назначение Лизы

Дата: 2026-08-27 (MSK)
Контур: свежая read-only сверка VLESS, Matrix и текущего назначения Лизы.

## Вопросы

1. Почему админка показывает, что с VLESS всё более-менее хорошо, хотя канал
   фактически не работает.
2. Почему Лиза находится на VLESS.

## Свежая проверка VLESS

Штатный `v7-service-matrix-test vless --probe-observation-only --pretty` выполнил
14 проверок без записи в Matrix и без изменения маршрутов:

- Telegram: OK;
- остальные 13 сервисов: FAIL;
- итог: `WARN`, `1/14`.

Основной свежий признак отказа — TLS connect error или connection reset. Локальный
интерфейс `tun0` существует, но это не доказывает работоспособность внешнего
сервиса.

## Почему админка показывала лучшее состояние

Канонический файл Matrix был обновлён по верхнему времени, но строка VLESS
содержала предыдущий замер `10/14`, выполненный примерно на 17 минут раньше
свежей read-only проверки. Админка показывает сохранённый Matrix snapshot, а не
каждую новую проверку в реальном времени. Поэтому её «сервисы работают» означает
«часть сервисов прошла последний сохранённый замер», а не «канал полностью
исправен».

Свежая проверка намеренно не записывала результат в каноническую Matrix, чтобы
диагностика не запускала побочные действия.

## Почему Лиза находится на VLESS

Лиза была создана по прямому запросу оператора с начальным egress `vless`.
Текущая каноническая запись подтверждает:

- `users.registry`: IP `10.7.0.125`, `current=vless`, `enabled=1`;
- identity и активное устройство связаны с именем Лиза;
- маршрут для этого IP ранее прошёл `V7_USER_ROUTE_CHECK=OK`.

В реестре VLESS при этом стоят ограничения для новых действий:
`production_assignment_allowed=false`, `autoswitch_allowed=false`,
`rebalance_allowed=false`. Они не отменяют уже созданное назначение и не дают
системе самопроизвольно перемещать Лизу. Поэтому она остаётся на VLESS, пока не
будет отдельно допущена governed-операция перевода через существующего owner.

## Эффект

- обычные пользователи не перемещались;
- маршруты и Matrix не изменялись;
- доказана частичная, а не полная работоспособность VLESS;
- назначение Лизы объясняется исходным запросом, а не текущей оценкой здоровья.

## Следующий шаг

Если нужно вывести Лизу с неработающего VLESS, выполнить отдельную governed
операцию перевода на автоматически выбранный здоровый канал через существующие
Planner → Candidate → Packet → Lease → Barrier → Apply owners. Перед этим нужно
обновить канонический Matrix snapshot штатным владельцем и подтвердить отсутствие
риска для обычных пользователей.
