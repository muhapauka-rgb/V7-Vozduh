# V7 — recovery по обязательным сервисам профиля

Дата: 2026-08-29

## Что проверено

Для Чака2 в текущем назначении профиль требует `instagram` и `telegram`.
Существующая Matrix содержала устойчивый сбой Instagram на текущем канале,
но эта запись уже не была свежей. У альтернативных каналов необходимые записи
также были устаревшими. Поэтому автоматический владелец не создал Packet и не
перевёл клиента: маршрут на неизвестную цель запрещён.

## Найденная логическая ошибка

Путь исполнения ordinary service-failure ошибочно требовал подтверждения
поломки всего канала, даже когда один обязательный сервис конкретного профиля
уже имеет свежую устойчивую поломку. Это сильнее необходимого условия и
противоречит назначению сервисных профилей.

## Исправление

В существующем `tools/v7-users-autoswitch`:

- источником обычного recovery теперь может быть свежий `PERSISTENT_FAIL`
  одного сервиса, объявленного обязательным именно для пользователя;
- при этом общий сбой канала остаётся самостоятельным основанием;
- проверка цели стала считать пользовательские обязательные сервисы
  обязательными при Candidate-проверке: неизвестное или устаревшее состояние
  цели не допускается;
- S11 и все действующие Candidate/Packet/Lease/Barrier/Authority проверки
  не менялись.

## Проверки

- добавлены два focused-теста: допустимый свежий profile-service recovery и
  отказ для устаревшей целевой проверки;
- `tests.unit.test_v7_users_autoswitch_policy`: 221 PASS;
- обновлены два устаревших регрессионных ожидания: soft quality-floor теперь
  остаётся видимым для ранжирования, но не делает свежую пригодную цель
  недоступной; проверка hard-consumer теперь проверяет текущий прямой Matrix
  consumer вместо исторического systemd-seam;
- полный целевой набор: 269 PASS (`autoswitch policy`, service-aware policy,
  role-based recovery, health deadline loop);
- штатный `tools/v7-safe-deploy --json` подтвердил allowlist и Runtime-delta,
  но законно остановился на `github_truth_check_failed`: локальный commit ещё
  не совпадает с опубликованной веткой. Runtime не менялся.

## Текущий Matrix blocker

Быстрый producer делает лёгкие наблюдения только для активных источников.
Он не обновляет успешную каноническую Matrix-запись цели, если эта цель сейчас
пуста. Одновременно зависший/долгий failure-producer может занимать свою роль
десятки секунд. Из-за этого Planner не получает свежую безопасную цель и
останавливается корректно, но позже целевого SLA.

## Следующий шаг

В существующем Matrix/health lifecycle закрыть этот gap: при свежем profile
incident подготовить ограниченную, owner-selected проверку подходящих целей и
жёстко ограничить длительность одной вспомогательной проверки. Затем провести
Polygon replay полного пути и только после успешного safe-deploy gate
публиковать и разворачивать исправление.
