# Admin: устранение ложной блокировки после завершённой операции

Дата: 2026-09-01

## Наблюдение

В интерфейсе ручная смена канала возвращала `Safe mode enabled`.
Это не было включённым операторским Safe mode: в текущем общем контракте
`enabled=false`. В нём осталась просроченная операция
`govexec_dcd4e7766e5eba8a704dc106` со статусом `CLOSED` и временем окончания
2026-08-31T20:57:10Z. Новое изменение маршрута она уже не могла разрешить,
но прежняя проверка админки трактовала любую невалидность этого старого окна
как бессрочную блокировку всех изменений.

## Исправление

Перед авторизованным действием оператора админка теперь проверяет только
строго определённый остаток завершённого окна: `CLOSED`, `operation`,
`enabled=false`, единственная причина невалидности — истёкшее время и нет
явного Admin Safe Mode. Такой остаток возвращается в исходное состояние
только существующим финализатором execution-control owner и фиксируется в
аудите.

Активное окно, явный Safe mode, повреждённый контракт или любая другая
неопределённость по-прежнему блокируют действие.

## Проверка

- `python3 -m unittest tests.unit.test_admin_realtime_truth tests.contracts.endpoint_inventory_test` — 27 PASS.
- Добавлены проверки: просроченное точное окно восстанавливается; при явном
  Admin Safe Mode восстановление не выполняется.
- На Runtime до публикации подтверждены активные `v7-admin-api.service` и
  `v7-health.service`; активных процессов переключения не было.

## Следующий шаг

Опубликовать и развернуть изменение через `tools/v7-safe-deploy`, затем
подтвердить в Runtime состояние `OPEN` и один безопасный операторский запрос
без ручного изменения маршрута.
