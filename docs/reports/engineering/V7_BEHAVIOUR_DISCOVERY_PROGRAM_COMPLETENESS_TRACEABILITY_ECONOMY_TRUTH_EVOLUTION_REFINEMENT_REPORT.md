## 5. What Was Added

Five internal BDP mechanisms were added:

| Mechanism | Purpose |
| --- | --- |
| Behaviour Completeness Model | Determines whether Behaviour Space coverage is sufficient for the declared scope. |
| Behaviour Traceability Model | Preserves the full engineering life of a Behaviour from identity through evidence, implementation/source, verification, Reality, consumers, and canonical/experience paths where applicable. |
| Behaviour Discovery Economy Model | Determines whether Discovery is unnecessary, targeted, full, or held. |
| Behaviour Truth Hierarchy | Defines official Behaviour evidence weight. |
| Behaviour Evolution Support | Accompanies Behaviour change over time using identity, traceability, Reality refinement, OMP/CPS, and Knowledge Evolution paths. |

These are program mechanisms only.

They do not create:

- new documents as canonical objects;
- new programs;
- new architecture levels;
- new owners;
- new truth sources;
- new Runtime;
- new OMP;
- new Planner;
- new memory;
- new storage.

## 6. Why Addition Was Necessary

| Need | Why BDP Required Explicit Mechanism |
| --- | --- |
| Completeness | Discovery Pass completion can prove the search ended, but not that Behaviour Space is covered enough for the decision. |
| Traceability | Candidate/evidence fields alone did not force an end-to-end life trace for Behaviour. |
| Economy | BDP could run unnecessary discovery even when existing evidence was sufficient. |
| Truth Hierarchy | Evidence existed, but BDP needed deterministic priority rules when production/runtime/implementation/tests/reports/architecture conflict. |
| Evolution | Identity dispositions existed, but BDP needed explicit lineage support for evidence refresh, implementation change, rename, versioning, supersession, contradiction, and manual review. |
