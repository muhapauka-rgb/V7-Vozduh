# V7 Track 7 — Release Lineage, Runtime Provenance & Reproducibility Foundation

Track 7 defines release truth without introducing CI/CD, package migration, containers, or a deployment rewrite.

## 1. Runtime Provenance Model

### Vocabulary

| Term | Definition |
|---|---|
| `release` | A named, reviewable deployment unit linking source, runtime manifest, verification, rollback material, and known warnings. |
| `release_id` | Stable identifier for one accepted runtime state, formatted `v7-runtime-YYYYMMDDTHHMMSSZ`. |
| `runtime_baseline` | A point-in-time snapshot of live runtime files, systemd bindings, checksums, state contracts, and warnings. |
| `deployment_snapshot` | Materialized manifest files produced during runtime inventory, such as `manifest.json`, `checksums.sha256`, `unit-summary.json`, and `contract-summary.json`. |
| `archive_lineage` | Mapping from archived files to original paths, hashes, mtimes, reasons, and source baseline reference. |
| `authoritative_executable` | Runtime executable proven active by systemd, shell-loop, admin subprocess, or operator workflow binding. |
| `production_only_tool` | Runtime executable present on VPS but not present in the repository by basename. It may be legitimate; it is not automatically obsolete. |
| `runtime_generated_artifact` | Runtime output rebuilt from authoritative state, such as summaries, caches, quality windows, or generated configs. |
| `state_authoritative` | Live state that must survive deploys and must not be overwritten from repo. |
| `runtime_local_pending_lineage` | Intentional or suspected legitimate runtime-local tool that lacks repo import/provenance notes. |

### Release Object

A V7 release object answers:

1. what source produced it;
2. what runtime manifest owns it;
3. what active executables are part of it;
4. what production-only tools remain outside source control;
5. what runtime contracts are authoritative;
6. what archive/rollback material exists;
7. what verification passed;
8. what warnings remain.

## 3. Production-Only Tool Governance

Known baseline from Block 3.3:

| Class | Count |
|---|---:|
| Unknown active-like tools | 117 |
| Runtime unknown tools also present in repo | 14 |
| Production-only unknown tools not present in repo | 103 |
| Referenced unknown tools | 90 |
| Unreferenced unknown tools | 27 |

Production-only classification vocabulary:

| Class | Meaning | Action |
|---|---|---|
| `intentional_runtime_local` | Tool intentionally maintained on VPS | Add owner, purpose, hash, workflow, release manifest entry |
| `missing_from_repo` | Tool should be source-controlled but is absent | Import with provenance notes or create clean repo equivalent |
| `generated` | Tool/artifact is generated by another source | Link generator and generation command |
| `operator_local` | Manual operator utility | Add owner and allowed usage; keep out of automated paths |
| `legacy_drift` | Historical artifact still executable | Candidate for future archive only after workflow verification |
| `runtime_specific` | Host-specific integration | Preserve in manifest; document why it is host-specific |
| `should_be_imported_to_repo` | Needed for reproducibility | Highest repo-convergence priority |

Never delete or archive production-only tools by count alone.

## 4. Runtime ↔ Repo Linkage

For each active runtime executable, lineage should become one of:

| Linkage | Meaning |
|---|---|
| `repo_source_exact` | Runtime file hash matches a repo source or generated release artifact |
| `repo_source_diverged` | Basename exists in repo but hash/content differs |
| `production_only_known` | Runtime-only but owned and documented |
| `generated_from_repo` | Produced by a repo generator with recorded inputs |
| `runtime_local_pending_lineage` | Temporarily accepted, not reproducible yet |
| `unknown_blocker` | Cannot be explained; blocks commercial release confidence |

Current status:

- baseline manifest exists from Block 3.1;
- archive manifests exist from Block 3.2 and 3.4;
- local repo does not currently contain the 103 production-only runtime tools;
- therefore a rebuild from repo alone is not yet credible.

## 5. Release Verification Gate

Before accepting a release:

1. Runtime manifest exists.
2. Checksums exist.
3. Archive manifests are linked.
4. `tools/v7-run-tests` passes.
5. `py_compile` passes for admin/core/release tools.
6. Endpoint inventory counts remain unchanged unless intentionally changed.
7. Runtime governance registry is updated.
8. Production-only tools are classified or marked `runtime_local_pending_lineage`.
9. Sensitive-state warning posture is reviewed.
10. Live deploy, if any, has explicit approval and rollback plan.
11. Post-deploy live verification passes:
    - `systemctl --failed`
    - `v7-killswitch-check`
    - `v7-user-route-check`
    - `v7-provisioning-reconcile-check`
    - `v7-observability-summary --pretty`

## 6. Reproducibility Blockers

| Blocker | Severity | Why |
|---|---|---|
| 103 production-only tools | High | Repo rebuild would omit live operational behavior. |
| Dirty/local source history | Medium/high | Source commit alone does not explain runtime. |
| Runtime-local manual edits | High | Manual server changes may not be reviewable. |
| Hidden PATH dependencies | High | Admin/operator workflows can call `v7-*` by PATH. |
| No accepted release manifest | High | Baseline exists, but no release object owns it yet. |
| Sensitive-state hardening pending | Medium/high | Commercial posture still needs staged hardening. |

## 8. Future Release Strategy

Bounded strategy:

1. Create a release manifest referencing the existing Block 3.1 baseline.
2. Mark all 103 production-only tools as `runtime_local_pending_lineage`.
3. Prioritize import/rewrite of tools that are:
   - referenced by admin/API;
   - mutating runtime;
   - provisioning/identity/policy related;
   - needed for rollback.
4. Keep operator-local utilities governed but not necessarily packaged.
5. Only after lineage is stable, consider a simple deploy process.

No CI/CD, package manager, or container platform is required for this stage.
